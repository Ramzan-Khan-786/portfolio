# Cloudinary media management — V1.3

Implementation status: **manual testing required**. No Cloudinary upload, application run, build, lint or test was executed for this release.

## Storage and configuration

Cloudinary is the canonical storage for all new CMS uploads. MongoDB stores content, references and metadata, not binary files. Multer buffers a single bounded file in memory; new uploads never create server-side files.

Set these backend variables without replacing existing secrets:

- CLOUDINARY_CLOUD_NAME
- CLOUDINARY_API_KEY
- CLOUDINARY_API_SECRET
- CLOUDINARY_FOLDER (optional; one safe root name, defaults to portfolio)
- CLOUDINARY_BACKGROUND_REMOVAL_ENABLED (optional, false by default)

The secret is never returned to the frontend. Operations and Media Library report configuration presence, not a live credential check. Missing configuration disables upload UI or returns 503; invalid credentials/quota/provider failures return a safe error.

Folders/public IDs are generated by the backend: portfolio/hero, profile, about, skills, tech-stack, projects/{validated-slug-or-unassigned}, showroom, resume/v{number}, documents and misc. Every object gets a UUID. Raw PDFs include the .pdf suffix. An original filename is display metadata only. Counter gaps after a failed upload are intentional.

## Pipeline and validation

Admin authentication → role check → operation limit → serialized CMS mutation lease → bounded multipart parser → category/MIME/extension/content checks → Cloudinary adapter → MediaAsset → content selection.

| Category | Input | Limit |
| --- | --- | --- |
| Hero, profile, about, projects, showroom, misc | JPEG / PNG / WebP | 8 MB |
| Skills, tech-stack | JPEG / PNG / WebP | 2 MB |
| Resume, documents | PDF | 5 MB, 1–50 pages |

Images are decoded with Sharp, limited to 25 million pixels, oriented and resized within 4096 × 4096, re-encoded to WebP, and stripped of metadata. Alpha is retained. Animation, SVG, renamed HTML and unsupported formats are rejected. Transparent PNG/WebP is the supported icon path.

PDF validation checks signature, parseability, encryption, page count and recursively inspects object dictionaries, arrays, references and stream dictionaries. Scripts, forms, attachments and dangerous actions are rejected; ordinary text, structure tags and safe HTTP(S)/mailto links remain supported. This is not antivirus.

## MediaAsset and references

MediaAsset stores useful Cloudinary IDs, resource/delivery types, folder/category, format/dimensions/bytes, original/display filename, SHA-256, alt text/caption/tags, uploader, timestamps and deletion/processing state.

Content uses mediaId, altText and caption. The API validates referenced images and hydrates only public-safe delivery metadata. The frontend never chooses a Cloudinary public ID or folder. Profile, hero, about, skills, project thumbnail/cover/gallery and showroom supporting images share these references.

Existing URL fields remain a fallback, not an upload path. To migrate: upload/select the replacement, inspect it, save the content, review the public page yourself, then clear obsolete legacy URLs if desired. No automated remote fetch/migration or destructive cleanup was performed.

## Upload, reuse and replacement

MediaUploader provides browse/drop, selected-file preview, filename/size/type, validation feedback, byte progress, processing, cancellation and error feedback. Browser upload completion is not Cloudinary completion: 100% changes the UI to Processing until the backend responds.

Media Library has paginated search, category/type filters, name/recent sorting, previews, metadata editing, usage details, URL copy and selection. PDFs have authenticated previews. Gallery order uses arrow buttons or drag handles; individual images carry alt text/captions.

Replacement always uploads a new object first. Select it in the content editor, then save. Existing references and the old object remain intact on upload/save failure. Old objects are not automatically deleted; use the library after reviewing usage. Cancel/connection loss cannot guarantee server cancellation after receipt: check the library before retrying.

## Deletion and failure recovery

Deletion requires explicit confirmation and checks current content references, including managed IDs, stored Cloudinary URLs and resume versions. Used assets return 409 with usage details. Unsaved editor selections are not persisted references; if another admin deletes one, the eventual content save rejects it safely.

CMS mutations are serialized through a MongoDB lease across API processes. A busy edit returns 409; retry after the current mutation completes. A stopped process's lease expires after three minutes. Do not concurrently modify content outside these APIs.

Deletion records deleting before contacting Cloudinary. A provider failure retains metadata in delete-failed state for retry. A successful provider delete followed by a DB failure may also leave retryable metadata; retrying tolerates Cloudinary's not-found result. There is no claim of an atomic transaction across Cloudinary and MongoDB.

If upload succeeds but metadata persistence fails, cleanup is attempted. Cleanup failure is logged with the generated public ID; an operator must review that orphan. No automatic sweep deletes unreferenced objects, since these may be intentionally staged or shared outside this CMS. Version deletion is performed through Resume Management, never by bypassing its publication guard.

## Delivery and performance

Public images use bounded Cloudinary c_limit resizing plus f_auto/q_auto. Noncritical content images load lazily. The public bootstrap resolves only referenced images; it never downloads the media library. PDFs use authenticated raw storage; signed provider URLs are used only by the backend. Public PDF access proxies only the current published version.

Cloudinary account delivery/strict-transformation policies and PDF delivery restrictions require owner acceptance. Remote legacy images are not downloaded or transformed unless they are recognizable unsigned Cloudinary delivery URLs.

## Background removal

Only skill/tech-stack images offer this optional operation. Enable it explicitly only after reviewing account capability and transformation costs. A signed background-removal transformation is fetched, validated and persisted as a separate transparent icon. The original and its references remain unchanged. Account errors, delayed processing and oversize output produce actionable failures, not fabricated success. Fallback: upload a transparent PNG or WebP.

## Deployment

Keep the shared directory with both applications. Allow backend outbound HTTPS to Cloudinary and, optionally, Google Drive. Back up MongoDB plus Cloudinary assets and retain logs durably. New uploads do not require a persistent filesystem, but legacy PDFs still do until migrated. Static-host CSP needs the actual image delivery host and local PDF worker/assets. See [deployment](DEPLOYMENT.md).
