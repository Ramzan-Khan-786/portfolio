# Portfolio V1 specification

Release: 1.3.0 — Cloudinary media CMS, versioned resume delivery, daisyUI policies and smoother navigation within V1. Implementation-only; manual testing required.

## Product architecture

A recruiter can read the developer identity/background, explore technical skills and published work, access a resume and contact channels. A technical visitor can use independently hosted projects inside the Engineering Showroom. Accounts are optional for browsing. Administrators manage content through role-protected screens backed by MongoDB.

No local imitation of TypeWriter, fake offline portfolio, invented analytics, synthetic experience, or disconnected Google login is presented as real content.

## Public pages

- Home: concise identity/headline/intro, optional portrait or initials, configured actions, selected work and actual counts.
- Profile: identity dossier, technical/current focus, education, highlights and interests.
- Skills: category-based technical ledger with optional icons and descriptions.
- Work: filterable published catalogue; individual detail routes carry full descriptions/screenshots/links.
- Showroom: compact tabs, large independent iframe, project context, source/live actions and failure/help controls.
- Resume: title/description/date, uploaded or external PDF, view/download, shared PDF.js preview, reused education/experience/skills/projects/achievements and links.
- About: longer narrative, working principles and optional experience.
- Contact: editable communication-focused heading/copy, email, channels and action.
- Custom pages: published plain-text content routes without overriding required system routes.

## Layout, motion and themes

Persistent navbar/footer frame a separately scrolling route. CSS entry transitions use 420 ms fade/translation. Gentle accumulated wheel/touch gestures at actual page boundaries may advance to the next/previous enabled core route. Content scrolling, nested scrolling and form interaction remain normal. Momentum locks, horizontal/modifier exclusion and direction thresholds prevent accidental repeated transitions. Explicit footer controls, clicks, browser history and scroll restoration remain available.

Reduced motion disables automatic routing and suppresses animations. Visitors can opt out persistently. Showroom remains non-scrollable while its parent heading/caption/chrome accepts route gestures. Events within its embedded application stay isolated.

Ten daisyUI palettes apply to public, auth and admin UI. The shared catalogue drives build/API/browser selection. CMS controls universal/random-reload/random-daily policy, enabled pool and optional visitor overrides; random assignment and visitor choice last only for the current document/tab visit, while daily selection uses the same UTC date everywhere. Typography, surfaces, borders, input fields, actions, status colors and shadows share tokens. Hybrid Tailwind plus colocated CSS keeps global styling focused.

## Content management

Separate modules: dashboard, hero, identity, profile details, about, skills, projects, showroom, Media Library, Resume Management, contact, socials, navigation, footer, themes, settings, custom pages, users, account and operations.

Structured repeaters manage timeline/link/action entries with reorder/remove controls. CRUD, publication/visibility/default/order settings persist through actual APIs. Dashboard values come from real database queries. User management lists paginated safe records and can suspend/restore normal users, never promote roles or disable administrators.

## Authentication

One cookie JWT system supports user/admin roles. Signup stores bcrypt hashes, validates fields and cannot accept privilege overrides. Login, me, logout and current-password-verified password change share the session contract; role/version/status are checked server-side.

Google uses its official browser button and official server ID-token verification with audience/issuer/signature/expiry, verified email and one-use nonce binding. New identities must create a portfolio password before account creation. Existing local emails require their current portfolio password before linking. Google subjects/email uniqueness prevent duplicates. Opaque pending proofs expire and are consumed atomically. Google tokens are neither persisted nor logged.

## Resume and files

Admin-only PDFs are constrained by type/header, parsing, size (5 MB), pages (1–50), encryption and active-content checks. Server-generated Cloudinary IDs prevent client-selected paths. Upload, scoped Drive import or library reuse creates a private draft. Preview acknowledgement precedes publication; one Resume pointer defines the public version. Old versions remain private for archive/rollback; confirmed deletion is restricted to inactive versions. SHA256 prevents identical version uploads.

A shared PDF.js viewer renders actual pages with text, safe links, search, zoom, fit width, page controls and fullscreen. Original view/download links remain the fallback. Download-button hiding cannot stop saving a viewable document. Validation is not antivirus; upload only trusted files and back up Cloudinary assets with MongoDB. Media Library applies bounded Sharp validation to images, managed references across content and usage-protected deletion. New uploads never use permanent local storage; old local PDFs remain read-only compatibility data.

## Backend and operations

Express namespaces preserve /api/public, /api/auth and /api/admin. Zod provides bounded schemas; Mongoose provides persistence/indexes. ContentSection, ResumeVersion, MediaAsset and ThemeSettings extend existing models without replacing saved content. A MongoDB lease serializes CMS mutations while provider/DB failures use compensation and retryable states. AuthAttempt uses expiry indexes and request-time checks.

Winston logs application/error/HTTP/auth/admin JSON events in separate rotating files: 5 MB each, five retained per category. Request IDs and whitelisted metadata provide correlation without sensitive headers, bodies, queries, hashes or tokens. Operations shows real readiness/configuration/uptime and the latest 50 non-HTTP process events. Startup/shutdown and unexpected failures use safe logging and bounded shutdown.

## Compatibility and verification

Saved admins retain role/password. Seed preserves customized records and upgrades only the exact legacy default navigation. New fields use defaults. Legacy showroom sandbox is normalized to iframe; no fake app is reintroduced. No automated test mutates the configured portfolio database.

No tests, lint, builds, servers or browser/provider verification were run for v1.3.0. Existing automated suites contain prior-contract expectations requiring updates; historical pass counts are labeled in [QA_REPORT](../QA_REPORT.md). Current acceptance is the comprehensive [manual testing guide](../testing/MANUAL_TESTING_GUIDE.md), including 320–1536px/mobile-landscape, provider failures, privacy, themes and gestures.

## Known limits and release gates

- Real Google client/origin/consent and actual TypeWriter embedding require deployment-specific acceptance.
- No live hosting or real database migration is performed by this implementation.
- No MFA, password-reset email, direct-signup email verification, analytics, rich HTML CMS, or embedded-app SSO.
- Configure Cloudinary and optional Drive before provider acceptance; legacy files/logs still require deliberate retention/backup. No automatic migration was run.
- Process-local rate limits/event windows need shared infrastructure for horizontal scaling.
- Local Chromium cannot prove Safari/Firefox/mobile hardware/PDF-viewer compatibility.
- SPA SEO/404 metadata is client-rendered; production headers, HTTPS cookies, backups/restore and monitoring remain operator responsibilities.

V2 articles/case studies and V3 AI are future versions, not partially implemented V1 controls.
